# 围绕项目级研究工作台重构

## 决策

下一轮迭代按“项目级研究工作台”进行重构，而不是在当前单文档 Demo 上做兼容性优先的增量扩展。

## 背景

当前代码有一些可参考片段，但用户已明确说明它很基础、基本不可用，不值得作为强约束保护。简历和 UI 方向都指向更完整的系统：项目、会话、资料、证据、知识候选、长期记忆、Agent 过程可视化和反馈闭环。

## 备选方案

- 保留当前实现并逐步打补丁：短期扰动小，但会继续把产品中心锁在 `sessionKey + documentId` 上，和目标项目模型冲突。
- 不建 Harness，直接一次性生成全部终局功能：表面速度快，但不可验证代码和边界混乱的风险很高。
- 在 Harness 控制下分片重构：开始写代码前慢一点，但更适合 Agent 并行，也更容易审计。

## 影响

- 正向影响：架构可以从一开始就对齐简历、UI 和产品模型。
- 正向影响：低价值旧兼容性不会扭曲新设计。
- 负向影响：旧接口可能被替换，而不是保留。
- 后续动作：F002 必须先定义合同，再进入实现，保证多个 Agent 可以并行而不互踩。

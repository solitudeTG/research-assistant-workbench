# F021.1 Self-Learning Closed Loop Reset Plan

## Why This Exists

F021 was marked completed, but manual service validation exposed a gap: the visible thumbs feedback path was missing. A zero-base review then found broader design drift. The implementation has useful pieces, but the full demo loop is not yet a stable, recoverable capability:

1. Confirmed project knowledge is visible in the Knowledge workspace, but is not yet a proven L2 recall/input signal for the next answer.
2. `feedback.applied` is generated by the backend, but lacks `sessionId` / `runId`, so the real SSE run stream cannot reliably show it.
3. Reloaded session messages now expose `answerId`, but not `runId`, so historical research-process trace recovery remains incomplete.
4. Some frontend tests assert source strings rather than executable UI/model behavior, which allowed visible feature gaps to pass.

The goal of F021.1 is not to expand the memory system. It is to make the existing F021 promise demonstrably true on the smallest closed loop.

## Scope

In scope:

- L2 confirmed project knowledge recall:
  - User-confirmed `knowledge_entry` must be available to the next project answer as L2/project knowledge context.
  - Trace must mark it as `memoryLayer=L2`, `sourceType=project_knowledge`, and `contextOnly=true`.
  - It must not increase citation evidence counts or paper evidence strength.
- Feedback trace integrity:
  - `feedback.applied` must carry enough answer/session/run identity to enter the real run event stream.
  - UI should not need a local-only fake event for the normal project API path.
- History recovery:
  - Project session message history must include `answerId` and `runId` for assistant messages when available.
  - Reloaded assistant messages should be able to show feedback controls and their research-process trace.
- Verification:
  - Each fix starts with a failing focused test.
  - Keep backend storage model unchanged unless a tiny association field is required and justified.

Out of scope:

- New vector database, reranker, user profile system, reinforcement learning, model fine-tuning, or parallel agent runtime.
- Treating memory context as citation evidence.
- Automatic AI writes into confirmed knowledge without user accept/edit-and-accept/manual creation.

## Acceptance Matrix

| Phase | Required visible capability | Current reset target | Verification |
| --- | --- | --- | --- |
| Phase 1 feedback loop | User can up/down vote an answer, choose evidence sources, and see applied evidence/chunk counts | Backend `feedback.applied` is SSE-visible for the answer run, not only locally projected | Backend focused test for event `sessionId/runId`; frontend/model test if local projection is removed or changed |
| Phase 2 L1/L2/L3 memory visualization | L1 working memory, L2 project/global knowledge, and L3 long-term memory are distinct context-only memory signals | Confirmed `knowledge_entry` appears as L2/project_knowledge/contextOnly in the next answer trace | Backend focused test on trace event and citation count separation |
| Phase 3 candidate to confirmed knowledge | Candidate stays pending until accept/edit-and-accept; accepted entry updates knowledge board | Existing behavior retained; no regression while adding L2 recall | Existing candidate and knowledge board suites remain green |
| Phase 4 demo loop | First answer creates candidate, user confirms it, second answer uses L2/L3 memory, user feedback affects later ranking | Minimum backend+frontend contracts support this path after reload | Focused suites plus live HTTP smoke; full provider demo remains a separate manual evidence item |

## Work Split

- Worker A owns L2 confirmed project knowledge recall and backend trace tests.
- Worker B owns feedback/session trace identity and backend history tests.
- Main agent owns Harness docs, integration, conflict resolution, final verification, and evidence update.

Workers are not alone in the codebase. They must not revert unrelated edits and must keep write scopes disjoint where possible.

## Test-First Plan

2. GREEN: add the smallest repository/service/query and orchestrator wiring needed to include L2 context.
3. RED: `FeedbackService.recordProjectAnswerFeedback` publishes `feedback.applied` with `sessionId` and `runId` for the answer.
4. GREEN: resolve answer context from existing persisted answer/event records and publish into the correct run stream.
5. RED: `GET /api/projects/{projectId}/sessions/{sessionId}/messages` returns assistant `answerId` and `runId` after reload.
6. GREEN: extend response contract and repository mapping.
7. Run focused backend suites, frontend model tests, `python .\scripts\knowledge_check.py`, and `git diff --check`.

## Rollback

If any F021.1 path destabilizes existing F008/F009/F015/F016/F020 behavior, rollback should remove only the new wiring and keep existing candidate, feedback score, event stream, retrieval diagnostics, and plan-execute evidence carry-through behavior intact.

## Closeout

2026-05-17: Completed. Code review and focused verification confirmed the reset targets are now implemented:

- L2 confirmed project knowledge recall: `KnowledgeBoardRepository.listConfirmedProjectKnowledge(...)` feeds `ProjectAgentRequest.projectKnowledge`; `DefaultProjectAgentToolLoop` includes that block in the prompt as non-citation context; `SupervisorService.publishMemoryTraceEvents(...)` emits L2 `project_knowledge` memory hits with `contextOnly=true`.
- Feedback trace identity: `FeedbackService.recordProjectAnswerFeedback(...)` resolves `AssistantAnswerRepository.findContext(...)` and publishes `feedback.applied` with `sessionId`, `runId`, and `answerId`.
- History recovery: `ProjectChatController` maps reloaded assistant messages through `AssistantAnswerRepository.findContextForSessionAnswer(...)`, and `ProjectSessionMessageResponse` includes both `answerId` and `runId`.
